# 15 - 队友部署包评审：ctf-deploy-bundle.zip

评审日期：2026-10-11
评审对象：`ctf-deploy-bundle.zip`（走微信收到），源出 **Kali 实验室 VM**（3072 MB / 2 vCPU，Coding2API 主上游 + Muteki 蜂群）
**结论：质量很高，可以给队友用。但有一条建议改（§3），另有一条千万别照搬（§4）。**

---

## 1. 完整性与保密性（我独立验的，没采信自述）

| 检查项 | 方法 | 结果 |
|---|---|---|
| SHA256 | 用包内 `SHA256SUMS.txt` 逐文件重算比对 | **9 / 9 全通过**，无缺文件、无篡改 |
| 密钥泄漏 | 10 类正则扫全部 10 个文件 | 命中 34 处 → **逐条看完全部是误报** |
| zip 附加数据 | 读 archive comment | 空 |
| 文件类型 | 只读列目录，**未执行任何脚本** | 14 条目（10 文件 + 4 目录），解压后仅 0.05 MB |

**34 处"命中"的实际身份：**

| 命中内容 | 性质 |
|---|---|
| `api_key: os.environ/AIWORK_KEY` | litellm 引用**环境变量**的语法，不是明文 |
| `SECRET=%s\nADMIN_PASSWORD=%s` | 生成 `.env` 用的 printf 格式串 |
| `SECRET= .env\|cut -d= -f2-` | 从 `.env` **读取**的命令 |
| `SECRET = 已存凭据不可解）` | 中文说明文字 |
| `<本机服务地址>` | 实验室 VM 内网 IP（见 §3） |

**→ README 声称的"包内不含任何密钥值（已做泄漏自检）"属实。**

## 2. 这份包好在哪（值得抄进我们自己的规范）

1. **三段式写法**：每一步都是「命令 → 期望输出 → 不匹配时怎么办」。
   对比我们现在的战例报告——**我们写结论多，写"不匹配怎么办"少**。
2. **处处标"measured on this box"**：区分"我实测过"和"文档上抄的"。
3. **§8 验收测试不可跳过**，而且验收标准是三条：
   ① 返回 flag 与 `solution/flag.txt` **字节一致**；
   ② 完成时间 ≤ ~90 s；
   ③ **grep run log 里的 `tool.start`**，确认 worker 真的调了本地工具 —— 不是瞎猜出来的。
4. **§12「已知不一致与未验证项（别当事实用）」** —— 主动把自己的不确定性列出来。
   这节里最有价值的一句：
   > 选型用的微题**分辨不出能力**：六个候选全对。它只能验可用性、时延和可靠性。
   > **真正的席位选择必须用你自己的真题跑 solve-rate × 时间 × 成本。**
5. **§11 回退清单**：每条改动都配一条 undo。
6. **§11「动手前先问人类」**的清单（关机、加自启、跑外部题、限流、轮换已泄漏的密钥）。
7. **明确写出工具的"agent 可用性"边界**：GUI 工具用不了（Burp Community 无驱动 API、Ghidra GUI 用不了，只能 `analyzeHeadless`）。

## 3. ⚠️ 唯一建议改的：内网 IP

`ctf-stack-deployment.md` 里出现了实验室 VM 内网地址 `<本机服务地址>`（2 处）。

- **不是密钥，不构成泄漏事故**；
- 但如果这个包要**公开分发**（GitHub / 群分享），等于把内网拓扑写进了文档。
- **建议**：分发前问一句"这个地址要不要脱敏"，或者确认是刻意保留的、给队友对账用的。

## 4. ⚠️ 千万别照搬：本机 Muteki 和它不是一回事

| 项 | 这个包（Kali 实验室 VM） | 本机 Muteki VM | 后果 |
|---|---|---|---|
| 内存 | **3072 MB** | 4096 MB | 决定能不能跑容器 |
| `worker_backend` | **必须 `local`**（作者给了两条独立理由：默认 5 席 × 2g 装不进 3 GiB；容器内 `127.0.0.1` 是自己，够不到宿主 loopback 的网关） | **`container`，且已验收可用** | **这条最容易被误抄** |
| 宿主用户名 | `chuxin`（NOPASSWD sudo） | `muteki` | SSH 命令、所有路径都不同 |
| Muteki 路径 | `~/ctf/tools/muteki` | `<本机路径>`（VM 内 `/home/<用户>/...`） | 脚本路径不同 |
| 主上游网关 | Coding2API（Trae 池）`127.0.0.1:8090` | WorkBuddy2API `<本机服务地址>:7863` | 端点完全不同 |
| 模型 id 写法 | `glm-5.3` / `deepseek-v4-pro-official` | `global:glm-5.3` | **最容易配错的一项** |
| 共享目录 | `/mnt/hgfs/ctf` → 宿主 `<本机路径>`，**rw** | 共享文件夹/剪贴板**已禁用** | 隔离策略相反 |
| Muteki 版本 | 0.4.2 | v0.4.2 | ✅ 一致 |

**记住：** "container 在 3 GiB 上不成立"是**对那台 VM 的结论**，不是对 Muteki 的结论。
本机的容器模式是通过验收的（`Docker-Worker-Verification.json`）。

## 5. 可以直接借用的（价值最高的几条）

| 借用点 | 用在哪 |
|---|---|
| **§8 验收设计**（已知答案题 + flag 字节比对 + grep `tool.start`） | **直接用来做 Muteki 首跑** —— 正好回答"全绿只证明管道通，不证明能解题" |
| **§9 比赛诚信**：worker 继承宿主网络、能搜公开 writeup，trace 审计显示**解题率大幅虚高，真赛场上等于失败** | 直接对应老板立的"AI 不当答案机器"规矩；比赛时要么题面禁止联网检索，要么限出网 |
| **§9 GUI 工具 agent 用不了** | 选工具/写派单时别把 Burp、Ghidra GUI 算进去 |
| **§5 在 prompt 里点名工具能显著提高使用率**（否则 agent 会自己手搓 Python） | 写派单 prompt 时把工具名写进去 |
| **§7 冷启动 root 变 `ro` 的 initramfs 缺陷 + 修法** | 本机 Muteki 若出现 `docker`/`containerd` 起不来，先查这个（特征：`dmesg` 有 `mounted … ro` 但没有 `re-mounted … r/w`） |
| **§12「微题分辨不出能力，要用真题跑 solve-rate」** | 印证了我们"用已知答案的真题做验收"的思路 |
| **三段式 + §12「别当事实用」** | 抄进 `模板\复盘模板.md` |

## 6. 一句话总结

**这是一份可以当范本的开源级部署文档**：
- 装得上（命令可复制）、验得出（有不可跳过的验收）、退得回（回退清单）、说得清（把不确定的单独列出来）；
- 唯一要改的是内网 IP 脱敏；
- 唯一要防的是**别把它的 `worker_backend=local` 结论搬到本机 Muteki 上**——两台 VM 的约束不同。
