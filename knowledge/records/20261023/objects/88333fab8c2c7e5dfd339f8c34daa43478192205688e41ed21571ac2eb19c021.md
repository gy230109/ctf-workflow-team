## 第二轮补验：x32 实际断点与单步（2026-10-12 追加）

上一轮对 x32 只验了"服务可达 + 工具发现"，**真断点、真单步没验**。本轮补上，已通过。

卡点与绕法（本机环境事实，往后别再试错）：

- **本机 gcc 是 winlibs 的 x86_64 单架构工具链**，`gcc -m32` 只有前端、没有 32 位库
  （`cannot find -lmingw32` / `-lgcc`）→ **编不出 32 位 PE**。
  绕法：**`nasm -f win32` + `ld -m i386pe`**，编一个不依赖任何导入的最小 PE32（只有 mov/add/ret/jmp），
  不需要 32 位 CRT，也就不需要 32 位库。
- 🔴 **nasm / ld 啃不动含中文的路径**（报 `unable to open output file`，路径变乱码）。
  编译工作目录必须用 ASCII（如 `%TEMP%`），**编完再拷回** `环境/验收/...` 留档。
- `ld --export-all-symbols` 在这套 nasm 目标上会报 `cannot export xxx: symbol not found`，
  所以验证**不依赖导出表**：用 `ListModules` 拿主模块基址 + PE 头的 `AddressOfEntryPoint`
  算出入口，再从入口反汇编里读 `call` 目标当断点位置。

实测结果（自建 32 位程序，`环境/验收/x64dbg-x32-20261012/summary.json`）：

| 项 | 实测值 |
|---|---|
| 文件 | PE32，`machine=0x014c` |
| 加载后暂停位置 | **`0x770E57F9` 在 ntdll**（系统断点），`status: LOCKED`、`isRunning: false` |
| 主模块基址 | **`0xE00000`**（ASLR，≠ PE 头的 `0x400000`） |
| 入口 | 基址 + `AddressOfEntryPoint(0x100d)` = `0xE0100D` |
| 断点 | `0xE01000` 命中 ✅ |
| 单步 StepOver | `0xE01000 → 0xE01004` ✅ |
| 寄存器 | 含 `eip`、**不含 `rip`** ✅（x32 与 x64 的关键差异） |
| 读内存 | `eip` 处 `83 C0 11` = `add eax,0x11`，与源码一致 ✅ |
| 收尾 | 删除断点 + `StopDebug` → `NO_TARGET` ✅ |

🔴 **本轮新发现的操作事实**：调试器进程**随发起它的调用/脚本结束被回收**。
x64 那次是 01:38 那轮起的、跨多次调用仍在；x32 由本脚本起、脚本一结束就 `reachable: false`。
→ **多步调试要在同一次调用（或同一个脚本）内一口气做完**，或者由人手动双击常驻。
跨调用接着调之前，先 `win_debug_status` 现测，不要假设会话还在。

## 放在系统中的位置

| 部件 | 职责 | 何时使用 |
|---|---|---|
| 主 agent / WorkBuddy / Muteki | 分析题面、提出假设、安排步骤、读取证据 | 统筹各题型 |
| HackTricks | 检索技术原文和适用条件 | 根据现有证据查资料 |
| Kali + GDB / Ghidra / jadx / Sage | Linux 动态调试、通用静态分析、Android 逆向、数学计算 | 按题目格式和执行环境选择 |
| x64dbg + MCP | Windows 原生 x86/x64 PE 动态调试：断点、单步、寄存器、内存、模块 | Windows Reverse 中静态分析不足时 |
| CTF-OS | 对外统一工具入口、参数校验、确认和证据归档 | 所有 agent 复用同一入口 |

x64dbg 不替代题目分类，也不是新模型或新的派单系统。先识别文件和静态分析，需要 Windows 动态证据时再启动对应架构。

### 本次发现的上游差异

- `GetDebugState` 可能返回 `status: LOCKED`，同时 `isRunning: false`；同一时刻其他响应尾部是 `[state] PAUSED`，并已成功读寄存器和内存。保留实际返回，不能把 `LOCKED` 单独判断为运行中或工具故障。
- 原插件 v1.5 的 `LoadBinary` 虽声明 `arguments`，实现没有传递该值。桥拒绝非空 `arguments`，避免假装已带参启动。
- `run` 等等待工具默认受本机 HTTP 预算限制。超时不会自动停止目标；先重新查询状态，再决定下一步，不要自动重试执行动作。
