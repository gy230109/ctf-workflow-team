这是一道 CTF 比赛题（类别：杂项 + 逆向混合）。工作目录里有三个附件：

- game.gb  —— 32768 字节的 Game Boy ROM
- kun.mp3  —— 128 kbps / 44.1 kHz 立体声，约 222.9 秒
- man.mp3  —— 同格式，约 228.2 秒

请自主分析并找出 flag。

===== 已确认的客观事实（可直接采用，不必重复验证）=====

1. game.gb 是结构合法的 Game Boy ROM：
   - 0x0104-0x0133 的任天堂 Logo 完整正确；
   - 头部校验 0x014D = 0xCC，按 "X = X - byte - 1" 复算一致；
   - 全局校验 0x014E = 0x830E，复算一致 —— 说明整个文件没有被事后改动过。
   - title @0x0134 = "GAME"；cart_type @0x0147 = 0x00 (ROM ONLY)；
     rom_size @0x0148 = 0x00 (32KB / 2 bank)；entry @0x0100 = 00 C3 50 01 (JP 0150h)。

2. ROM 的 bank1（偏移 0x4000-0x7FFF）整块是 0xFF，完全未使用。
   全部内容都在 0x0000-0x3FFF 这 16 KB 内。
   尾部件 0x33A0 附近是真实 LR35902 代码（例如 `f0 40 cb 77 20 05 21 00 98`
   = LDH A,($FF40) / BIT 6,A / JR NZ / LD HL,$9800，即等 VBlank 后写图块图的绘图例程）。
   0x0D40 之后那段"重复的 7-8 字节模式"（`22 72 2B 5E 23 56` /
   `32 2B 5E 23 56 23 6E 26`）经核对**是编译产物里的 LR35902 惯用指令序列，不是数据表**，
   那些可打印 ASCII 串是巧合。

3. **这个 ROM 已经用 pyboy 跑通过，是个 Flappy Bird 类小游戏，名字叫 "FlappyPig"**：
   - 启动后标题画面显示 `FlappyPig` 与 `PRESS START`；
   - 按 START 进入游戏：横版城市背景 + 一只小猪，画面右侧有"手指指向 A 键"的提示；
   - 死亡后显示 `RESULT` / `BEST` 两个分数（初始都是 0）。
   - **BG 图块图（0x9800）里出现的图块索引 33..70 正好对应 ASCII 33..70**，
     也就是说这个游戏的字体是 ASCII 映射的：**屏幕文本可以直接按 ASCII 读出来**。
     （例如 `RESULT` = 52 45 53 55 4C 54）

4. 两个 mp3 的 ID3v2.4 标签在文件偏移 138 处结束（syncsafe size = 128）。
   源文件元数据为 major_brand=mp42 / Lavf56.25.101 / LAME3.99.5，即由 MP4 抽轨而来。

5. kun.mp3 与 man.mp3 **不是同一段音频的微改**：
   两者从偏移 184 起就不相同（184 处正是 Xing/Info 头的 TOC，因为两首时长不同必然不同），
   同长度区间只有约 1.6% 的字节相同，接近随机基线 → 逐字节 diff 没有意义。
   **长度差 = 84428 字节 ≈ 5.3 秒，正好是 man 比 kun 长的那 5.3 秒。**

6. kun.mp3 整段波形包络几乎恒定（每秒 RMS 稳定在 7000-11000，峰值 0.986 FS）；
   man.mp3 前 6 秒是静音然后渐入。两首都看不出隐藏的周期信号（自相关无显著峰）。

7. 🔴 **两个 mp3 的频谱图已经做过了，结论是「没有频谱隐写」。**
   已用 `ffmpeg -lavfi showspectrumpic=s=1400x700:scale=log` 对两首各出一张，
   都是正常音乐的宽带能量分布，**没有任何文字/图案/摩斯电码形状**。
   **不要重复做频谱图**，这条路已经排除。

===== 🔴 一个必须纠正的误判（上一轮就是栽在这里）=====

上一轮把 ROM 偏移 **0x1C92** 附近的一段代码误判成了"加密字符串"
（当时读出的 `ADLOBPUVCQSRBPNMBCT` / `BCDVWEXCDE`）。

**那是误判。它的真实身份是 GBDK 编译器内联展开的 `set_bkg_tiles()` 调用，不是密文。**

原始字节（0x1C8E 起）：

```
1C8E: 58        LD E,B
1C8F: 51        LD D,C
1C90: 3E 8A     LD A,$8A
1C92: 12        LD (DE),A      ; BC[0]  = $8A
1C93: 68 61 23  LD L,B / LD H,C / INC HL
1C96: 36 41     LD (HL),$41    ; BC[1]  = 'A'
...
1D4C: 36 54     LD (HL),$54    ; BC[19] = 'T'
1D52: 78 C6 14 6F 79 CE 00 67   ; HL = BC + 20
1D5A: 36 8B     LD (HL),$8B    ; BC[20] = $8B
1D5C: C5        PUSH BC
1D5D: 68 61     LD L,B / LD H,C
1D5F: E5        PUSH HL
1D60: 21 06 07  LD HL,$0706
1D63: E5        PUSH HL
1D64: 21 07 05  LD HL,$0507
1D67: E5        PUSH HL
1D68: CD A7 33  CALL $33A7
```

**关键点（这几条是事实，不是猜测）：**

- 那 19 个字母不是"数据"，而是 **`LD (HL),n` 指令的立即数字节本身**。
  用 `grep 36` 的粗暴扫描去"提取字符串"，必然扫出一串看似随机的大写字母 —— 这是**扫描伪影**。
- `$8A` 开头、`$8B` 结尾，夹着 19 个 ASCII 字符 —— 这是**图块索引数组的头/尾标记**。
- 末尾的 `CALL $33A7` 带着三组参数 `(BC, $0706, $0507)`，
  **`$33A7` 就是往 VRAM 背景图块图写数据的例程**（0x3385 那段是它的 STAT/VBlank 等待前导）。
  → 这段代码的作用是：**在背景层坐标 (x=7, y=5) 处画一块 6×7 的图块**。
- 结论：`ADLOBPUVCQSRBPNMBCT` 是**游戏正常显示的一段文字**，**不是 flag 的密文，也不是待解密的串**。
  不要再围绕它做"密码学猜测"（凯撒 / 倒序 / 重排 / 异或），那是死路。

===== 建议方向（仅供参考，不要被这几条限制）=====
- **优先用 pyboy 把游戏真跑起来**，用**文本形式**检查各画面（标题 / 游戏中 / RESULT），
  看是否有分数阈值或其他条件会触发额外文本。
- 关注 RESULT / BEST 的判定逻辑：是否有"达到某个分数才显示某段文字"的分支；
  **可以在 pyboy 里直接改内存里的分数变量来触发分支**，不必手工玩。
- ROM 在 16 KB 内塞了完整游戏，找找是否有**未被正常流程触发**的文本或画面
  （例如某个只在特定条件下才调用的 `set_bkg_tiles` 调用点）。
  已知的绘图调用点：`$33A7`（背景图块）、`$3342`/`$335F`（批量复制）、`$0E4A`、`$230B`、`$23BA`、`$2388`。
- 两个 mp3 与这个游戏是什么关系（配乐？干扰项？还是另有编码）。
  **注意：频谱图这条路已经排除**（见事实 7）。若要继续查音频，应考虑非频谱手段：
  尾部追加数据、帧间空档、DTMF、倒放、或两首音频的**差异段**（那 5.3 秒）。
- 也可以从"为什么恰好是这两个文件名 kun / man"切入，考虑它们在题目语境里的含义。
