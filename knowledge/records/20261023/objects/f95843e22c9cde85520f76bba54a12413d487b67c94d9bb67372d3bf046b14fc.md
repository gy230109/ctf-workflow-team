# 20 · Muteki 空转探针（stall probe）

- **日期**：2026-10-11
- **工具**：`tools/muteki_stall_probe.py`
- **动机**：老板问"体系如何"时，暴露出**"失败静默"**这个结构性弱点

---

## 0. 一句话

> Muteki 失败时**不报错**：进程还在、事件还在滚、状态看着正常，
> **但已经 37 分钟没调过任何工具了**。这个探针就是**唯一能看出这件事的东西**。

---

## 1. 它要解决什么（真实案例）

| | ✅ run-0006（成功） | ⚠️ run-0889（未完成） |
|---|---|---|
| 题目 | EasyRsa | GameBoy-FlappyPig-v4 |
| 时长 | 97.1 s | 3398.2 s（56.6 分钟）|
| `tool.start` 次数 | 12 | **54** |
| 间隔 中位 | 3.0 s | 5.6 s |
| 间隔 最大 | 6.0 s | 128.8 s（**已恢复**）|
| **尾部停滞** | 15.0 s | **2216.8 s（36.9 分钟）** |
| `run.finished` | ✅ | ❌ |
| 结束方式 | 出 flag 收尾 | 被人（Codex）`pause` |

### 🔴 关键洞察（差点把我自己带偏）

**第一版判断是错的。** 我只看了 run-0889 尾部 5 分钟的日志（全是 `retry_scheduled→done` 的 30 秒循环），
就下了"**静默空转 = 没有工具调用**"的结论。

查完整事件流才发现：**run-0889 的工具调用次数比成功的 run-0006 还多（54 > 12）**，
而且它干的活很实：`xxd` 扫 ROM、**`r2 -a gb`（radare2 的 Game Boy 架构）反汇编**、
装 pyboy 跑模拟器、写脚本找指针 —— 甚至 `submit-fact` **提交了隐藏串 `PS03R49UE576R421RE8`**（和我解出来的同一个）。

> **所以"有没有在调工具"完全分不开好 run 和坏 run。**
> **只有"多久没调"能分开。**

这条也修正了我 18:20 版记忆里的措辞 —— 不是"空转不报错"，
而是**"前 20 分钟在真干活，最后 37 分钟彻底静默，而外部看不出区别"**。

---

## 2. 判据

```
停滞时长 = now − 最后一次 tool.start 的时间戳
```

| 判定 | 条件 |
|---|---|
| `DONE` | 见到 `run.finished` / `progress.brief phase=solved` |
| `STALL_DEAD` | 停滞 ≥ `--dead`（默认 600 s） |
| `STALL_WARN` | 停滞 ≥ `--warn`（默认 180 s） |
| `RUNNING` | 其余；或**有工具在飞且未超 `--tool-timeout`** |
| `INIT` | 还没开始，未超 `--grace`（默认 300 s） |

### 阈值取值依据（不是拍脑袋）

- `--warn 180 s`：正常样本**最大间隔 128.8 s 且自行恢复** → 180 s 留足余量
- `--dead 600 s`：超 10 分钟无工具调用，基本不会自愈
- `--grace 300 s`：preflight（装镜像、拉依赖）可能几分钟没工具调用

---

## 3. 防误报（重要）

"长时间没有新 `tool.start`"**也可能是合法长任务**（例如跑几分钟的 hashcat 爆破）。
所以再加一条：**存在"在飞"的工具**（`tool.start` 了但还没 `tool.result`），
且间隔未超 `--tool-timeout`（默认 600 s）→ **不算停滞**。

实测 run-0889 收尾时在飞 3 个、间隔 2216.8 s > 600 s → **仍然正确判死**。

---

## 4. 用法

```bash
# 离线复盘（吃一个 run 事件 jsonl）
python tools/muteki_stall_probe.py --run-jsonl <run.jsonl>

# 在线盯（走 Muteki SSE 事件流，实时告警）
python tools/muteki_stall_probe.py --run-id run-0889 --minutes 30

# 自检（拿两个已知真实样本）
python tools/muteki_stall_probe.py --selftest

# 机器可读
python tools/muteki_stall_probe.py --run-jsonl x.jsonl --json
```

环境变量（**不写死路径**）：`CTF_MUTEKI_BASE`、`CTF_MUTEKI_PW_FILE`、`GM_BASE`。

### 看点

- **`距上次工具`** ← 主判据
- **`间隔 中位/最大`**：即使当前 `RUNNING`，若 `gap_max` 很大，说明它**卡过又自己缓过来了**（值得看一眼）
- **`工具在飞`**：>0 说明有长任务在进行，属正常

## 6. 已知局限（不许当成万灵药）

1. **只对 Muteki 的事件模型有效**。判据绑死 `tool.start` / `tool.result` 两个事件类型；
   若上游改了事件名，探针会失效 —— **换版本后必须重跑 `--selftest`**。
2. **在线模式依赖本机与 VM 的时钟一致**（Muteki `ts` 与本机 `time.time()` 同为 Unix 秒）。
   时钟偏差大会导致停滞时长算歪。
3. **它只报"死没死"，不报"为什么死"**。根因（额度争用 / planner 选席失败 / 模型空转）
   仍要另查。
4. **样本只有 2 个**（run-0006 成功、run-0889 空转）。阈值是从这 2 例校准的，
   **样本太少**；每多积累一次真实失败，就应该回头看阈值是否要调。
