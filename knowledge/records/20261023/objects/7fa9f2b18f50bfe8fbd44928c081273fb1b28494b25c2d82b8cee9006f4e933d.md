# 04 · 踩坑与教训

> 规则：**只记真实发生过的**。每条格式 = 现象 / 根因 / 修法 / 教训。
> 新坑追加到末尾，不要删旧条目。

## A 类：环境与工具

### A1 · 本机 Bash 的 PATH 是坏的
- **现象**：`ls`、`grep`、`date`、`wc`、`file`、`bc` 全部 `command not found`；shell 还报 `dirname: command not found`。
- **根因**：PATH 被其它程序污染，MSYS 基础工具目录不在其中。
- **修法**：每条命令前加
  ```bash
  export PATH="/usr/bin:/bin:/c/Windows/System32:$PATH";
  ```
- **教训**：**先怀疑环境，再怀疑文件丢了**。不要在"文件是不是没了"上浪费时间。

### A2 · 没有 pycryptodome
- **现象**：`import Crypto` → `ModuleNotFoundError`。
- **修法**：用 `openssl enc` CLI 代替；或用纯 Python 手写 ECB（`pip install` 也可，但离线环境别指望）。
- **教训**：CTF 环境里**能用的东西比你想象得少**。先 `which` 一遍再写脚本。

### A3 · Windows Python 的 `/tmp` ≠ Git Bash 的 `/tmp`
- **现象**：脚本写了 `/tmp/x.bin`，下一次命令找不到。
- **修法**：一律用**绝对 Windows 路径**，或统一 `BASE` 变量。
- **教训**：跨 shell/解释器时，**路径是最大的隐性 bug 源**。

### A4 · `openssl -nopad` 自测时 `bad encrypt`
- **现象**：为了快速自测，把文件截断到 16 字节再解密 → `bad encrypt`。
- **根因**：`-nopad` 要求输入长度是块大小的整数倍。
- **修法**：自测时用完整块；或改用 `-aes-128-ecb`（默认 PKCS7）。
- **教训**：**看到报错先确认"是不是我自己的测试脚手架坏了"**，别急着怀疑算法。

### A5 · ⭐ "脚本目录"和"数据目录"混用一个变量 → 一设环境变量就崩
- **现象**：把工具链搬到 D 盘、统一成 `BASE = os.environ.get('GM_BASE', 脚本目录)` 之后，
  一设 `GM_BASE=<题目产物目录>` 就报
  `FileNotFoundError: '[CTF_ROOT]/战例库/.../artifacts\dn.py'`。
- **根因**：**同一个 `BASE` 被两种语义共用**：
  ① `import dn.py`（**代码依赖**，永远在脚本旁边）；
  ② 读 `embedded.dll` / `gamemessage`（**数据文件**，跟着题目走）。
  一设 `GM_BASE`，`dn.py` 也跟着跑到数据目录去，于是找不到。
- **修法**：拆成两个变量 ——
  ```python
  SCRIPT_DIR = os.path.dirname(os.path.abspath(__file__))
  BASE = os.environ.get('GM_BASE', SCRIPT_DIR)   # 只有数据文件用 BASE
  # import dn.py 一律用 os.path.join(SCRIPT_DIR, 'dn.py')
  ```
- **验证方式**：修完后用 D 盘环境**重新生成一遍证据文件**，
  与搬迁前的旧产物 `diff` —— **逐字节一致**才算"搬对了"（本次 `emb.il` 7996 B 完全一致）。
- **教训**：解耦路径时，**先问"这个路径是跟着代码走，还是跟着数据走"**。
  一个变量承担两种语义，迟早在设环境变量那一刻爆掉。
  而且这种 bug **在"不设环境变量"时完全不显形**，只有真换工作目录才暴露 —— 所以搬家后必须**实测一次**。

## B 类：逆向技术

### B1 · `FieldRVA` 表的列顺序写反
- **现象**：`TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'`。
- **根因**：ECMA-335 里 `FieldRVA` 的 schema 是 **`[RVA(u4), Field(ti)]`**（RVA 在前），
  我写成了 `[Field, RVA]`，于是把 RID 当 RVA 去 `r2o()`，返回 `None`。
- **修法**：
  ```python
  rva = struct.unpack_from('<I', d, q)[0]
  fr  = struct.unpack_from('<I' if pe.ti(4) == 4 else '<H', d, q+4)[0]
  ```
- **教训**：**元数据表的字段顺序必须逐字对齐规范**。而且 `None` 参与运算的报错，
  第一反应应该是"**某个查表函数返回了 None**"，不要往类型系统上想。

### B2 · IL 反汇编器"逻辑错位"追了一小时
- **现象**：反汇编到某个 `call` 之后全部错位，报 `index out of range ... op=0x72`。
- **根因**：两根：
  ① `ldstr` 的操作数是 **token `0x70xxxxxx`**，我当成 `#US` 堆的原始偏移；
  ② 小方法头（`0x02 | size<<2`）与大方法头（`0x1b 0x30 ...`）没区分。
- **修法**：
  ```python
  operand = repr(pe.us(v & 0xffffff))        # ldstr 取低 24 位
  if (b0 & 3) == 2: csz = b0 >> 2            # tiny header
  else: fh, maxst, csz, lv = struct.unpack_from('<HHII', d, off)
  ```
- **教训**：写解析器时**先给每个字段做"自洽检查"**（尺寸、范围、magic），
  一旦错位立刻抛错并报告位置，而不是静默算出垃圾。

### B3 · ⭐ 把"编译器生成的数组名"误当成"密钥派生提示"（**本战例最大的坑**）
- **现象**：`Blackjack.dll` 的 `#Strings` 堆里有个 64 位 hex：`E64C3151...AE07`；
  `BlackjackConsole.exe` 里有个 `166CCA32...DF70`。算了一下，**正好等于
  `SHA256("qwb2022BlackJack")` / `SHA256("Brainstorming!!!")`** →
  当时判断"代码里算过 SHA256，密钥就是哈希结果"。
- **后果**：写了一个"200 组候选密钥 × 5 种模式"的爆破，**一次调用烧掉 56 秒，全部失败**（可打印率 ≈ 0.42，等同随机）。
- **真相**：那串 hex 是 C# 编译器给 `<PrivateImplementationDetails>` 里**静态字节数组**自动起的**字段名**
  （命名规则就是内容哈希）。它**不是**密钥派生、也不是线索，纯粹是编译产物。
- **正确动作**：看到 `ldtoken tok0x4000003` + `InitializeArray`，
  应该走 **`FieldDef → FieldRVA → RVA → 文件偏移`** 去读**原始字节**，而不是拿哈希当密钥。
- **教训（三条）**：
  1. 元数据里出现"奇怪的长 hex 标识符名" → **优先怀疑是编译器命名习惯**；
  2. 看到 `SHA256(x) == 常量` 这种"完美巧合"要**警惕**：它可能只是数组名，跟密码学无关；
  3. **不要在没看 IL 之前写爆破脚本**。

### B4 · 漏掉最外层的 `XOR 0x22`
- **现象**：拿 `Brainstorming!!!` 直接 AES 解密 `gamemessage`，永远乱码。
- **根因**：EXE 的 `Main` 在解密**之前**还有一段 `for (i) buf[i] ^= 0x22;`。
- **修法**：见 `03-SOP` §2.3 —— **拿到分组密码题，必须先把"加密前的字节级变换"扫一遍**。
- **教训**：**AES 外面几乎总会套一层廉价混淆**（XOR / 加常量 / 字节反转）。
  只试"纯 AES"是最容易卡死的地方。

### B5 · `Padding=Zeros` 与 openssl
- **现象**：不加 `-nopad` 时 openssl 报 `bad encrypt`。
- **根因**：`.NET` 的 `PaddingMode.Zeros` 不做填充，openssl 默认按 PKCS7 校验最后一字节。
- **修法**：`-nopad`。
- **教训**：枚举值要背。`PaddingMode`: None=1, PKCS7=2, **Zeros=3**；`CipherMode`: CBC=1, **ECB=2**。

### B6 · 忘了确认"窄化转换"，白担心 192 bit 未知量
- **现象**：一开始以为要解 3 个 64 位整数（192 bit），觉得 z3 没希望。
- **根因**：没先读 `ParseKey`。
- **真相**：`key[i] = (keys[i] >> (j*8)) & 0xFF` ⇒ 只取**低 4 字节** ⇒ 未知量只有 **96 bit**。
- **教训**：⭐ **看到"宽整数 → 窄字节数组"的转换，第一件事就是确认取的是哪几位。**
  这一步能把"不可解"变成"可解"，成本几乎为 0。已固化为 `03-SOP` §7.2。

## C 类：策略与预算

### C1 · 前 3 次调用浪费在无效爆破上
- **现象**：8 次调用/120 s 的预算，第 4–7 次全花在爆破；最后连"验证"的额度都没留。
- **根因**：**没有分诊就动手**。正确的顺序是"认题型 → 找字面量 → 定算法栈 → 定密钥 → 计算 → 验证"。
- **教训**：预算模式下，**第 8 次调用永远留给验证**。已固化为 `00-训练总纲` §3.1。

### C2 · 没有为"慢操作"预留预算
- **现象**：z3 求解实测 **129 s**，单步就超过 120 s 上限。
- **根因**：没估过单步成本。
- **教训**：任何"可能 > 60 s"的操作（爆破、SMT、大矩阵）**必须先估时**，
  并在预算模式下换更省的做法（先纯 Python 小范围试、先线性化推高位）。

### C3 · 没有前置工具，只能靠 grep 猜
- **现象**：首轮全程只有 `grep` + `openssl`，拿不到 `set_Mode/set_Padding` 的实参。
- **根因**：本机没有 ILSpy / dnSpy / dotnet-ildasm。
- **教训**：⭐ **工具要前置准备好**。现在 `tools/dn.py` + `tools/il.py` 已经能覆盖 90% 的 .NET 题。

## D 类：流程与纪律

### D1 · "解出来是乱码 → 换个密钥"这种循环是陷阱
- **现象**：反复换密钥、换模式，每次都能得到"不像明文"的结果，然后继续换。
- **根因**：缺少**判据**，变成随机搜索。
- **教训**：每次失败都要能回答"**这次失败排除了什么**"。排除法要能收敛。

### D2 · 差点把"看起来像 flag"当成解出
- **现象**：某个错误密钥解出来的字节里恰好有个 `}`，一度想宣布成功。
- **修法**：确立红线 —— **必须独立复算 + 枚举唯一性 + 常量溯源**三重验证。
- **教训**：已固化为 `03-SOP` §8 的验证清单。

### D3 · 结论与"未验证的假设"混在一份文档里
- **现象**：首轮报告里"密钥是 SHA256 结果"被写成接近结论的表述，其实是失败假设。
- **修法**：报告里**分区**：`已验证事实` / `未验证假设（明确标注）` / `未完成步骤`。
- **教训**：**猜测不能和结论同框**。这既是给评审看，也是防止下一次自己被误导。

### D4 · 时间口径不透明
- **现象**：首轮"命令内累计 89 s"与"墙钟超过 120 s"是两回事，如果混写会失真。
- **修法**：报告里**分别列**工具内耗时 / 墙钟耗时 / 是否越限。
- **教训**：**口径要写清楚**，尤其当结论会被用来做对比时。

## F 类：Kali 协同（2026-10-09 实测新增）

### F1 · ⭐ 本机 Windows 自带的 `scp.exe` / `sftp.exe` 整体损坏

- **现象**：桥接 `put` 报
  `SCP failed: C:/Windows/System32/OpenSSH/scp.exe: pipe: Unknown error`，
  而**同一个 `ssh.exe` 完全正常**。
- **排错过程**（值得记住，因为很容易在错的方向上烧时间）：

  | 试过的假设 | 结果 |
  |---|---|
  | 需要 `-O`（旧 SCP 协议）绕过新 SFTP 路径 | ❌ 加不加 `-O` 都 `pipe: Unknown error` |
  | 是 Git Bash 的环境污染 | ❌ 在 PowerShell 工具里、干净 PATH 下同样失败 |
  | 是 `scp` 解析 `ssh` 时 PATH 里找了别的 ssh | ❌ 显式 `-S` 指定同目录 ssh 也失败 |
  | **是这台机器上 scp/sftp 自身坏了** | ✅ 反向证据：**`sftp.exe` 也报同一个错**；而 WorkBuddy 自带 PortableGit 的 `scp` 一路 `rc=0` |

- **判据（下次 30 秒判定）**：`scp` 连"最简形式、不带任何 `-o`、输出重定向到文件"都秒失败，
  且报的是 **`pipe: Unknown error`**（本地管道创建失败，**根本没到联网那一步**）
  → 别再怀疑密钥/known_hosts/网络，直接判定为**客户端本体问题**。
  版本：`OpenSSH_for_Windows_9.5p1, LibreSSL 3.8.2`；`scp -V` 在这个版本不支持（可见是新版 scp）。

- **性质**：需要 `fork 子进程 + 本地管道` 的程序（scp/sftp）全挂，
  单进程的 `ssh` 不受影响 —— 所以**只要不用 scp，一切照常**。

### F2 · 修法：把桥接的传输改走 **ssh 数据通道**，彻底不用 scp

最小改动、且不依赖任何第三方新路径（比"改用 PortableGit 的 scp"更稳，
因为 PortableGit 带版本号目录 `versions\1.2.0\`，升级即失效）：

```python
# kali_bridge.py
self.ssh("/bin/cat -- <remote>")                  # 下载：ssh 的 stdout 就是文件字节
self.ssh("/bin/cat > <remote>", data=payload)     # 上传：ssh 的 stdin 就是文件字节
```

要点（都是踩过的）：

1. **必须加 `-T`**（不分配 TTY）。二进制走 TTY 会被换行转换/回显污染。
2. 远端路径用 `shlex.quote()` 包住；命令整体作为**一个 argv 元素**传给 ssh。
3. 上传时若目标以 `/` 结尾，要**自己补上文件名**（`cat > /path/` 会失败）。
4. 用**正则**区分方向，不要用 `":" in path`（`C:\...` 也含冒号）：
   `^(?P<user>[^/\\@]+)@(?P<host>[^:]+):(?P<path>.*)$`，
   且**校验 host 必须等于已固定的 VM IP**（防止误发到别的主机）。
5. 传输**不负责校验** —— 由原有 COMMIT/FETCH 的 SHA256 逻辑兜底，职责不变。
6. 改前先备份（本文件与 Codex 共用）：`kali_bridge.py.bak-20261009-scpfix`。

- **验证**：388 KB 的 `BlackjackConsole.exe`（含大量 `\x00`）上传后 SHA256 与本地一致 →
  证明二进制通道无损坏。

### F3 · PowerShell 会把桥接的 `Evidence:` stderr 行渲染成 `NativeCommandError`

- **现象**：三条命令实际 `exit=0`、JSON 完整，但输出里混着红色
  `+ CategoryInfo ... NativeCommandError`，看着像失败。
- **原因**：`local_log()` 把证据路径打到 **stderr**，PowerShell 在 `2>&1` 合并时按错误处理。
- **修法**：**看 `exit=` 和 JSON 内容，别看颜色**。要干净输出就别用 `2>&1`（证据路径其实值得留）。

### F4 · Kali 控制台是 GBK，中文把长输出截断

- **现象**：体检脚本的 JSON 打到 stdout，回传后**中间被截断**、中文变乱码
  （`文件系统` → `鏂囦欢绯荤粺`）。
- **修法**：**大输出一律写文件再 `fetch`**，不要指望 stdout。
  （桥接的 stdout 单流上限 1 MiB，截断会标记，但控制台编码问题它管不了。）

## G 类：验证方法（2026-10-09 新增）

### G1 · ⭐ 自研解析器**必须**用第三方实现交叉验证

- **背景**：`dn.py` / `fld.py` 是手写的 CLR 元数据解析器。
  它一旦错了，**错得很像对的** —— 表能读出来、字段名是字符串、偏移看着也合理，
  但全链路的结论会一起错。
- **做法**：换一个**完全独立的第三方实现**（PyPI `dnfile`，底层 `pefile`）再解析一遍，
  逐项比对**可客观比较**的字段：表行数 / RVA / field 序号 / 字段名 / 同一 RVA 读出的字节。
- **收益**：**零成本、零安装到 Kali**，却比"在 Kali 上装 mono"覆盖得更准
  （mono 只验 IL，dnfile 验的是我们更容易写错的**元数据表 + RVA 映射**那一层）。
  实测两张样本 **FAIL 0 条**（见 `05-环境与Kali协同规划.md` §3.6）。
- **教训**：**"自己写的验证工具"不能作为唯一证据。** 验证链上每一环都该有外部锚点。
  这条和 `03-逆向SOP` 里的"验证三条红线"是同一件事的两个方向：
  前者要求**结论**被独立复算，这里要求**工具**被独立复算。
- **残留**：第三方工具**覆盖不到的部分要明确写出来**（dnfile 不做 IL，所以 `il.py` 的操作码解码
  没被它验证）。**不许因为"工具验过了"就默认全部都验过了。**

## H 类：Factor 密码题与模型协作（2026-10-10 新增）

### H1 · 素数幂模数先展开公共因子

`p⁷q` 的 φ 含 p⁶。`e*d=1 mod φ` 与 `inverse(e,N)` 组合，能把秘密 d 写成很小的余项；`s/N=t/(pq)+d/N`，有效分母是 pq。先试整数连分数再决定是否上格。本题三层均由连分数解出，算法约 1.719 s。

### H2 · 有约束不等于约束有信息

第二层 d1,d2 仅 672 位，源码 `delta≈N^0.65625` 却约为 2686 位量级；`abs(d1-d2)<delta` 太宽，不能据此推断两个私钥特别接近。先比实际量级。另 `len(bin(N))` 包含 `0b`；本题该层实际 4094 位。

### H3 · 逆指数解密必须检查单位与可逆性

因子恢复后检查 `gcd(e,φ)`；非 1 要走模根恢复。重复素数幂模数上的幂映射不能无条件当作整个剩余类环的置换。本题所有密文均是单位，可逆指数在单位群上给出唯一明文；归档校验器另用 λ(N) 验算。

### H4 · 把本地模型参与和独立解出分开记录

Qwen3:8b 一次非思考源码分析，4096 上下文、1400 输出 token，含加载 53.641 s。它识别了 RSA，却没有给出构造性连分数攻击，且因长度结束。保留原回复和输入；不把“先分解 N”当作攻击方法，也不从一轮受限调用得出模型能力上限。本题这一轮未调用 WorkBuddy DeepSeek。

### H5 · 对照条件不同，不硬造 DPO

### I1 · ⭐ `github.com` 这个域名解析不了，但别的 github 子域全都正常

拉 `morluto/rea` 时的原始现象：

```
socket.gethostbyname("github.com")   -> gaierror [Errno 11001] getaddrinfo failed
Resolve-DnsName github.com           -> 由于超时时间已过，该操作返回
Test-NetConnection github.com -443   -> TcpTestSucceeded = False
```

**同一时刻**这些却是好的：

| 主机 | 结果 |
|---|---|
| `codeload.github.com` | 20.205.243.165，能下 tarball（HTTP 200，`application/x-gzip`） |
| `api.github.com` | 20.205.243.168，能取仓库元数据 |
| `gh-proxy.com` | 104.18.42.163，HTTP 200 |

继续排查的三个结论：

1. `nslookup github.com 8.8.8.8` / `223.5.5.5` / `119.29.29.29` **全部超时**
   → 本机到外部 DNS 的 53 端口被挡，只能用系统解析器；而系统解析器**唯独**对 `github.com` 卡死。
2. `hosts` 文件（`C:\Windows\System32\drivers\etc\hosts`）**无写权限**
   （`net session` → 非管理员账户）→ 没法用写 hosts 的办法绕。
   *（顺带发现 hosts 里已经有人手工加过 `172.64.145.209 chatgpt.com`，说明这是老毛病了。）*
3. 本机代理 `http://127.0.0.1:2147`（`HTTP_PROXY`/`HTTPS_PROXY` 环境变量）**也到不了**
   `github.com`（`ProxyError`）—— 但它是能到 `codeload` 和 `gh-proxy.com` 的。

**教训**：**不要因为一个域名解析失败就断定"整个外网不通"。**
先分别测几个**子域**（`codeload` / `api` / `raw`），往往立刻就能找到绕过去的路。
本例里 `codeload` + `api` 都是好的，等于信息基本都能拿到。

### I2 · ⭐ 镜像站 `gh-proxy.com` 能代理 **git 协议本身**，所以能做真正的 `git clone`

**不是所有 GitHub 加速站都行。** 判据是这一条 URL 的**返回类型**：

```
https://<镜像>/https://github.com/<user>/<repo>.git/info/refs?service=git-upload-pack
     -> Content-Type: application/x-git-upload-pack-advertisement   ✅ 能 clone
```

2026-10-10 实测：

| 镜像 | 结果 |
|---|---|
| `gh-proxy.com` | ✅ 200 且类型正确 → **能 clone** |
| `ghproxy.net` | 403（只做 release/archive 下载） |
| `kkgithub.com` | SSLError |
| `gitclone.com` | ReadTimeout |
| `bgithub.xyz` | ProxyError |
| `hub.gitmirror.com` | DNS 失败 |

**最省事的用法**不是改 clone 地址，而是给**单个仓库**加一条局部重写：

```bash
git config url."https://gh-proxy.com/https://github.com/".insteadOf "https://github.com/"
```

好处：`.git/config` 里 `origin` 存的**仍是官方 URL**，但 `git fetch` / `pull` /
`submodule update` 全部自动走镜像；以后网络恢复了不用改回来。
（**不要**随手加 `--global`，除非确定长期没有直连。）

实测结果：`morluto/rea` —— 54543 个对象 / 36 MB pack / 2343 个文件，**18 秒**克隆完成，
HEAD 与 `api.github.com/.../commits/main` 给的 SHA 一致。

细节见 [`08-REA逆向分析MCP.md`](08-REA逆向分析MCP.md) §6。

## J 类：2026-10-11 新增（BMP 位深谎言 / PDF 子集字体 / 段切换 crackme / 栈上诱饵）

### J1 · ⭐ BMP 头字段 `biBitCount` 会撒谎

- **现象**：`threebody.bmp` 头部写 `biBitCount=24`，但按 24 位读出来图像是坏的；
  文件大小 `1,009,338 = 138 + 580*4*435`——**只有按 32 位算才对得上**。
- **根因**：题目**篡改 BMP 头谎报位深**（头是 V5、124 字节，实际数据是 32bpp BGRA）。
- **修法**：**用文件大小反推位深**：`文件大小 − 像素数据偏移 = 宽×高×每像素字节数`；
  或直接试 32bpp 并按 `BGRA` + `FLIP_TOP_BOTTOM` 解析。把头部字段改成 32 即可正常显示。
- **教训**：**不要让"头部声明"盖过"文件大小算出来的事实"**。位深/宽高/通道数与体积对不上时，先信体积。

### J2 · ⭐ PDF 子集字体 `ToUnicode` 恒等映射 → 直接抽文本必得乱码

- **现象**：`adobesecretreader` 的 41 份 PDF 用 `pdftotext` 之类直接抽，得到 `u _ /S/I&3DSiI3I&…` 这种乱码。
- **根因**：每份 PDF 用**独立置换过的 DejaVuSansMono 子集字体**，且 `ToUnicode` 是**恒等映射**——
  代码点 → 字形被洗牌，但 Unicode 映射照抄代码点，所以"抽文本"永远错。
- **修法**：抽 `FontFile2` 的 TTF，用**随包原字体**做**字形轮廓逐字节比对**，重建 代码点→真实字符 映射。
  本题 95/95 字形全部命中。
- **教训**：**字体乱码不等于内容加密**。先看是不是子集字体 + 恒等 ToUnicode，再走轮廓比对。

### J3 · ⭐ 32↔64 位段切换 crackme（`cmp cs` + `retf`）

- **现象**：`x96` 是 ELF32 却**无 section header**，常规工具反汇编到入口就乱。
- **根因**：入口 `cmp cs, 0x23` 后 `retf`，跳到 `0x33:0x804806c`——**从 32 位段切进 64 位段**，
  后面的字节要按 **64 位**解释（"中立的双方读同样字节却解释不同"）。
- **修法**：认出 `cmp cs,0x23/0x33` + `retf` 就是段切换；对目标偏移**按 64 位反汇编**；
  校验循环 `buf[i] ^ (ror64(K, i)&0xff)` 直接反推输入；到 32 位 compat 环境实跑见 `Correct!`。
- **教训**：**ELF32 也能跑 64 位代码**。无 section header + `retf` 要立刻想到段切换。

### J4 · ⭐ 栈上写死的字符串可能是**诱饵**

- **现象**：`task_qwxf` 的 `main` 里写死了 `qiangwangxianfengjiushini`，一眼像答案，实际**全程未被使用**。
- **根因**：出题人放干扰串；真正的逻辑是"对输入做 base64 编码再与另一常量比对"。
- **修法**：判断某字符串是否参与逻辑，**看它被哪条指令引用**；真正要比对的常量在比对循环里。
  本题正确输入 = 目标 base64 串的解码（`flag{mafakuailaiqiandaob}`），实跑见 `yes, you are!`。
- **教训**：**"像答案的串" ≠ "答案"**。先确认引用关系，再下结论。

### J5 · 纪律：不许搜题解答案；若搜过，必须如实记入"功劳认定"

- **现象**：`threebody` 解题中途曾用搜索引擎读到公开题解，被老板当场纠正"不许作弊搜答案"。

## K 类：2026-10-12 新增（glibc `rand()` 复现 / CTF-OS 运维三坑 / 发布同步盲区）

### K1 · ⭐⭐ 复现 glibc `rand()` 必须用 31 元素 lagged-Fibonacci，而不是自己"凑"的位数

- **现象**：`Vanguard-ezre` 里字母表由 `srand(85)` + 洗牌生成。自己写的 `rand()`（344 元素）
  推出来的 `srand(85)` 前几个数是 `243151441, 1058630469, …`，与真实 glibc 不符，
  导致"反推出的 c0 非法、题目无解"的假悖论，卡了很久。
- **根因**：**glibc 的 `random()` 是 TYPE_3 加法反馈发生器**：`deg=31, sep=3`，
  即 `state[i] = state[i] + state[i-3]`（模 2^32），返回 `>> 1`；且 `srand()` 后用
  **310 次** `rand()` 做 warm-up。位数/参数错一个，序列就全错。
- **修法**：按 TYPE_3 正确实现（31 个元素、`f=3`、`srand` 用 Schrage 公式初始化 31 个数、
  再空转 310 次）。正确实现下 `srand(85)` 前 8 值 =
  `2023096691, 1266327893, 1509554281, 1471411733, 1860715705, 1596953071, 339788306, 1172629246`。
- **验证手段**：**别猜，直接对表**——在 Kali 上用 `ctypes.CDLL('libc.so.6'); libc.srand(seed)`
  取真实序列，跟自己的实现逐项比对，一致了再往下推。
- **教训**：**libc 的伪随机数是有标准算法的，不许"差不多就行"**。复现 RNG 前先拿到真值对表；
  凡是"链路上游数据不符"导致的"无解"，八成是 RNG/编码这类底层复现错了，回去把地基夯实。

### K2 · ⭐ CTF-OS 两个运维坑（`kali_run` 吞 `local_file` / 健康检查太弱导致旧进程一直被复用）

- **现象 a**：用 `kali_run` 传 `local_file` 想先上传再跑，结果 Kali 上一直报
  `没有那个文件或目录`——文件根本没上传。
- **根因 a**：`tool_kali_run` 只调 `runtime.kali_execute(a, argv)`，**漏传 `local=`**；
  schema 也没声明 `local_file`。于是参数被**静默忽略**，不报错但也不生效。
- **修法 a**：`tool_kali_run` 里取出 `local_file` → 校验存在 → `kali_execute(a, argv, local=local)`，
  并把 `local_file` 加进 schema（与 `_mk_remote_tool` 的写法对齐）。命令里用 `../input/<文件名>` 引用。
- **现象 b**：改动源码（如新增 `wp_*` 工具）后，**线上 8787 服务仍是旧工具集**，别人调 `wp_init` 报"未知工具"。
- **根因 b**：常驻守护 `ctf_bootstrap.py` 的健康检查 `EXPECTED_TOOLS` 只含 4 个工具
  （`math_gcd/kali_run/muteki_dispatch/rea_status`），旧进程恰好满足 → 判定"健康"→ **一直复用旧进程**，
  且遇到"端口占用但检查不过"时选择直接报错（**不杀进程**）。所以旧版本会长期存活。
- **修法 b**：改完源码后**要重启常驻服务**才生效。现在守护已自带"自愈"：发现端口被占但
  `/tools` 不健康时，会**只杀命令行确认为 `ctf_os.py` 的监听进程**再重新拉起（见 K3）。
  手动兜底时：停掉 `ctf_os.py --host … --port 8787` 的旧进程，用 `config/startup.json` 里的
  python 重新拉起（`--host 127.0.0.1 --port 8787 --log … --audit …`，与守护一致），
  再 `GET /tools` 核对工具数。**勿动 `--stdio` 进程**（那是 MCP stdio 通道，杀了会断）。
- **教训（通用）**：**"源码已改" ≠ "线上已生效"**。改完共享服务必须重启并**核对 `/tools` 工具数**；
  同时注意：**"参数被静默忽略"比"参数报错"更坑**——危险的静默失败要改成显式报错。

### K3 · ⭐⭐ 守护必须"子进程死了自己活着"，否则杀一次服务就永久没人管

- **现象**：手动重启 8787 服务时用 `StopCommand` 停掉了 HTTP 子进程，结果**常驻守护
  `ctf_bootstrap.py --serve` 也跟着退出了**，端口空着、`CTF-OS-常驻` 计划任务变成 `Ready`
  （不是 Running），服务再也没人拉起 —— 正是"别人使用时会踩"的那种坑。
- **根因**：`resident_server` 里是
  ```python
  child = subprocess.Popen(args, ...); result = child.wait()
  if result: return result          # ← 子进程非 0 退出（被杀/崩溃）时守护直接 return 退出
  ```
  Python 的 `Popen.wait()` 返回**退出码**：被 `taskkill /F` 杀 → 非 0 → 守护 `return` →
  **进程结束**。于是"服务崩了"= "守护也没了"，彻底失去自愈能力。语义刚好写反了：
  干净退出（0）反而会重拉，异常退出（≠0）却会自尽。
- **修法**：异常退出**只记录 + 退避，不结束守护**，回到循环顶部重新拉起：
  ```python
  if result:
      print(json.dumps({"ctf_os": "restarting", "exit_code": result}, ensure_ascii=False), flush=True)
      time.sleep(5)                 # 退避后回到 while 顶部：健康检查 → 端口空闲 → 重新 spawn
  ```
- **顺带**：`_port_listener_pids(port)` + `_is_ctf_os(pid)` 实现了"端口被占但不健康时，
  **只杀命令行确认为 `ctf_os.py` 的监听进程**"，避免误杀别的程序；无法确认则显式报错、不盲杀。
- **验证（真机实测，不靠推理）**：改完源码 → `py_compile` 通过 → 只 kill 守护的 launcher/real 两个
  PID（**不带 `/T`**，保住 HTTP 子进程）→ 重启计划任务 → 再 `taskkill /F` 掉 HTTP 监听进程
  （PID 42616）→ 观察：**守护 PID 仍在**、6 秒内**新监听 PID 45324** 起来、`GET /tools` 仍是 62 个工具。
  → 证明"杀服务不再连带杀守护，且能自愈"。
- **教训（通用）**：**写守护/看门狗时，第一件事就是问"被守护的进程死掉后，我还在不在？"**
  异常退出恰恰是最需要守护介入的时刻，绝不能让它顺带把守护终止。
  另外：终止进程要区分**只杀目标 PID** 与 **`/T` 连坐整棵树**——重启守护时用后者会把服务一起带走。

### K4 · ⭐⭐ 已发布的团队包里还留着 `kali_run` 吞 `local_file` 的老 bug（同步盲区）

- **现象**：本机 `tools/ctf_os.py` 早就修好了 K2（`runtime.kali_execute(a, argv, local=local)`），

- **根因**：分发包不是"直接复制源码"，而是 `build_team_bundle.py` 按白名单**重新生成**的

- **教训（通用）**：⭐ **"本机已修" ≠ "已发布已修"。** 只要分发包是"重新生成的"，

  否则修复只活在本机；这类盲区在本地永远自测不出来。

### K5 · ⭐ 发布仓库里 CRLF / LF 混着存：写文件换行不统一 → 暂存目录永远"有改动"

- **现象**：`分发/ctf-workflow-team` 里 `git status` 一直显示少数文件 Modified，
  但 `git diff --ignore-cr-at-eol` 是**空的**。
- **根因**：仓库 blob 是**混合换行**——早年经 GitHub API 上传的 blob 存的是 CRLF，
  这次用 `git` 从 Windows 工作区提交的新 blob 被 `core.autocrlf=true` 规范成了 LF。
  而打包脚本用 `write_text(...)` 在 Windows 上默认写出 CRLF，
  于是命中的正好是那几个"LF blob"的文件。
- **修法**：**别急着改打包器的换行**（我试过统一成 LF，结果 41 个文件全部变成 Modified，
  立刻回滚）——先确认白名单里到底哪种换行占多数，再统一。
- **验证（真机实测）**：写 LF → `git status` 41 个文件全 M；写回 CRLF → 只剩那 4 个 M。
  两次结果都留了记录，说明当前基线是 **CRLF 为多数**。
- **教训**：修改文本产物生成方式时，**必须先量一次基线**（数一下 Modified 文件个数），
  不要凭"LF 更规范"的直觉动手；换行这种事，一次误改能让整仓库看起来全被改过。
