## §1 第 0 分钟：文件形态分诊（成本 ≈ 0）

```
1. 列目录：文件名 / 体积 / 修改时间
2. 每个文件取前 64 字节 hex
3. 按下表查 magic
```

| Magic（hex 或 ascii） | 判定 | 下一步 |
|---|---|---|
| `4D 5A` (`MZ`) | PE（exe/dll/sys） | §4 .NET？看 `BSJB` |
| `7F 45 4C 46` | ELF | 查架构 / 是否 static |
| `50 4B 03 04` (`PK`) | ZIP/JAR/APK/DOCX | 解包看内部 |
| `1F 8B` | gzip | 解压 |
| `89 50 4E 47` / `FF D8 FF` `/GIF8` | 图片（可能隐写） | 看 §2.3 |
| `BSJB` | **.NET 元数据根**（CLR） | 走 §4 |
| `CA FE BA BE` | Java class | `javap -c` |
| `00 01 00 00 00 FF FF FF FF` | **BinaryFormatter / NRBF** | 走 §5 |
| 无 magic + 长度整除 16 | 疑似分组密码密文 | 走 §2 |
| 无 magic + 长度任意 | 流密码 / XOR / 已破坏头 | 走 §2.3 |

**同时必做的三件事**（都很便宜）：
- `len(file) % 16`、`% 8`、`% 4` —— 分组线索；
- 字节熵（0~8）—— 7.9+ 基本是加密/压缩，3~5 是代码/文本混杂；
- 全量打印可打印字符串（`[ -~]{4,}`），**一次拿完**，别分多次 grep。

## §2 密码学判据树

### §2.1 分组密码 —— 模式判别（**必须先做，免费**）

```python
from collections import Counter
b = [d[i:i+16] for i in range(0, len(d)-15, 16)]
c = Counter(b)
print(len(d) % 16, [(i, c[x]) for i, x in enumerate(b) if c[x] > 1])
```

| 现象 | 结论 |
|---|---|
| **存在重复块**（尤其同一块出现 ≥3 次） | **ECB** ✅ |
| 无重复块，长度整除 16 | CBC / CFB / OFB / 或"数据本身无重复的 ECB" |
| 长度不整除 16 但有规律 | 流密码 / 已去填充 / 非分组 |
| 长度整除 8 但不整除 16 | DES / 3DES（8 字节分组） |

> ⚠️ **不要跳过这一步直接爆破密钥**。ECB 的重复块是免费的确定性判据。

### §2.2 拿到分组密码后，必须查清的 5 件事

1. **算法**：AES / Rijndael / DES / 3DES / SM4？（看 `RijndaelManaged` / `Aes` / `DESCryptoServiceProvider` / `SM4`）
2. **模式**：`set_Mode(?)` 的**实参**
   `CipherMode`: CBC=1, **ECB=2**, OFB=3, CFB=4, CTS=5
3. **填充**：`set_Padding(?)` 的**实参**
   `PaddingMode`: None=1, PKCS7=2, **Zeros=3**, ANSIX923=4, ISO10126=5
4. **密钥来源**：是静态数组（走 `FieldRVA`）？还是 `+` 拼接 / `SHA256` / `MD5` / `PBKDF2`？还是用户输入经 `Base64`？
5. **IV 来源**：常量 / 零 / 密文前缀 / 与 Key 同源

> 📌 **`Padding=Zeros` 用 openssl 要加 `-nopad`**，否则报 `bad encrypt`。
> 📌 若解密出来"前 16 字节像样、后面全乱"→ 大概率 **IV 不对** 或 **加密前还做过异或**。

### §2.3 加密前的字节级变换（**最容易漏**）

出题人几乎都会在 AES 外面套一层廉价变换。**必查清单**：

- [ ] 单字节 XOR（跑一遍 0..255，看输出熵/可打印率是否有拐点）
- [ ] 多字节重复 XOR（`repeating-key`，看长度是否与 key 长度成倍数关系）
- [ ] 每个字节 `+k` / `-k` / `~x`
- [ ] 字节序翻转 / 4 或 8 字节分组内反转
- [ ] 只有**前 N 字节**被变换（文件头）

> 本战例：`gamemessage` 先做 **`buf[i] ^= 0x22`** 再 AES。
> 这一步漏了，会把 200 组密钥全试成乱码 —— 这就是首轮翻车的直接原因。

### §2.4 流密码 / PRNG 判别

| 特征 | 可能 |
|---|---|
| 输出与明文等长，无填充 | 流密码 / XOR keystream |
| 代码里有 `>>` + `^` + `& 1` 反复出现 | **LFSR**！走 §6 |
| 有 `MersenneTwister` / `Random(seed)` | MT19937（624 个 32 位输出后可还原状态） |
| 有 `HashAlgorithm` 反复调用且计数递增 | 计数器模式 / 哈希链 PRNG |

## §3 编码与封装识别（不要手算，靠特征）

| 特征 | 判定 |
|---|---|
| 只有 `A-Za-z0-9+/=`，长度 %4==0 | Base64 |
| 只有 `A-Za-z0-9+` | Base32 / Base58 |
| `%XX` 密集 | URL encode |
| 偶数长度 + 大量 `\0` | UTF-16LE |
| `BSJB` 在某偏移 | 内嵌 .NET 程序集（配合 §4） |

## §4 .NET / CLR 逆向速查

### §4.1 表号速查（ECMA-335 II.22）

| 表号 | 名称 | 关注字段 |
|---|---|---|
| 0x00 | Module | Mvid |
| 0x01 | TypeRef | Name, Namespace |
| 0x02 | **TypeDef** | Name, Namespace, Extends, FieldList, MethodList |
| 0x04 | **Field** | Flags, Name, Signature |
| 0x06 | **MethodDef** | **RVA**, Flags, Name, Signature |
| 0x0A | **MemberRef** | Class, Name（外部调用全靠它） |
| 0x0B | Constant | 常量（含 `ldc` 出的字符串/数字） |
| 0x1D | **FieldRVA** | `[RVA(u4), Field(ti)]` ← **RVA 在前！** |
| 0x11 | StandAloneSig | `calli` 签名 |

### §4.2 三个必须记住的"隐藏手法"

1. **静态数组藏在 FieldRVA**
   `lc.i4.s 16; newarr; dup; ldtoken tok0x4000003; call InitializeArray`
   → 明文不在 IL 里，必须走 `FieldRVA`（`tools/fld.py`）。

2. **元数据里的长 hex 标识符名 = 编译器给静态数组起的哈希名**
   本次：`E64C3151...AE07` == `SHA256("qwb2022BlackJack")`，
   `166CCA32...DF70` == `SHA256("Brainstorming!!!")`。
   **这不是密钥派生，是 `<PrivateImplementationDetails>` 的字段命名习惯。**
   → 正确动作：去找那段静态数组的**原始字节**，而不是拿哈希当密钥。

3. **方法体可能不在 MethodDef 里**
   用 `tools/orphan.py` 扫 `.text` 里的 fat header（`1b 30`）。

### §4.3 IL 阅读顺序（别从第一行开始读）

```
① 找 call/callvirt/newobj 的 token → 知道调了什么 API
       RijndaelManaged / Aes / CreateDecryptor / set_Mode / set_Padding / Deserialize
② 找 ldtoken + InitializeArray → 静态数组
③ 找 ldstr → 所有字符串字面量（本题的关键分支全靠这个找）
④ 再回头看控制流（brfalse/brtrue）与循环边界
```

> 📌 **第一遍读 IL 时，先只看 §4.3 的 ①②③，不要试图理解整个函数。**
> 本战例里 `T1..ctor` 有 300+ 条 IL，真正决定 flag 的只有 3 处。

## §5 序列化流（BinaryFormatter / NRBF，MS-NRBF）速查

**合法头**：

```
00 01 00 00 00 FF FF FF FF 01 00 00 00
│  │  └ RootId ─┘ └ HeaderId ┘ Major Minor
└ RecordType 0x00 = SerializedStreamHeader
```
（`HeaderId = 0xFFFFFFFF`，`MajorVersion = 1`，`MinorVersion = 0`）

**RecordType 速查**：

| 值 | 名称 |
|---|---|
| 0 | SerializedStreamHeader |
| 1 | ClassWithId |
| 2 / 3 | ClassWithMembers / ClassWithMembersAndTypes |
| 4 / 5 | SystemClassWithMembers / ...AndTypes |
| 6 | BinaryObjectString |
| 7 | BinaryArray |
| 8 | MemberPrimitiveTyped |
| 9 | MemberReference |
| 10 | ObjectNull |
| 11 | MessageEnd |
| 12 | BinaryLibrary（**程序集名在这里**） |
| 15 / 16 / 17 | ArraySinglePrimitive / Object / String |
| 21 / 22 | MethodCall / MethodReturn |

**BinaryType 枚举**（MemberTypeInfo 里）：0=Primitive, 1=String, 2=Object, 3=SystemClass, 4=Class, 5=ObjectArray, 6=StringArray, 7=PrimitiveArray。

**分析套路**：

1. 先 `find(b'MZ')` / `find(b'BSJB')` —— **内嵌程序集通常直接躺在流里**；
2. 再 `find(b'BinaryLibrary')` 附近找程序集全名；
3. 本战例：明文里 `MZ` @ 5099 → 抽出 `embedded.dll`（5632 B），
   真正的算法全在里面 ⇒ **不必解析完整个对象图就能拿到答案**。

> ⚠️ **安全红线**：分析时**只做字节级结构识别**，不喂给 `BinaryFormatter.Deserialize`。
> 这类题目本身就是"反序列化利用"（已知 gadget：`TypeConfuseDelegate`、
> `ActivitySurrogateSelector`、`TextFormattingRunProperties`），
> **执行即中招**。本战例全程未反序列化。

## §6 自定义 PRNG / 流密码（LFSR 类）——建模清单

遇到 `>>` + `^` + `& 1` 密集的循环，按这 8 条逐项确认，**漏一条就全乱**：

1. **寄存器个数与位宽**（`ulong` = 64 bit；看 `newarr`/局部变量类型）
2. **抽头位置**：每个 `shr.un k` 的 `k`，全部记下
3. **反馈合成**：`xor` 链 → 反馈位 = 各抽头异或
4. **移位方向**：`shl 1` = 左移（低位进反馈）；`shr 1` = 右移
5. **更新与输出的先后**：**先更新后取样**？还是反过来？（本题是**先更新**）
6. **输出函数**：单一寄存器？还是多寄存器混合？
   - 线性（只有 `xor`）→ 可用 GF(2) 高斯消元，**不需要 z3**，快得多
   - 非线性（含 `and` / `or` / `mul`）→ 走 §7 z3
7. **取样位**：`shr.un k` 后 `& 1` 的那个 `k`（本题 `z>>32`、`x>>30`、`y>>31`）
8. **打包顺序**：每个 bit 是落到字节的 **bit0（LSB-first）** 还是 **bit7（MSB-first）**？
   - LSB-first：`ks[i/8] |= bit << (i%8)`
   - **MSB-first**：`ks[i/8] = (ks[i/8] << 1) | bit` ← 本题用的是这种
   - 计数器的自增时机（`i%8==0` 时先自增，还是先写后自增）

> 本战例的 8 条对应值：
> 3 个 64 位寄存器；taps = `[29,28,25,23]` / `[30,27]` / `[31,30,29,28,26,24]`；
> 移位 `shl 1`；**先更新后输出**；输出 `(X1&X2)^(~X1&X3)`（非线性）；
> 取样位 32/30/31；**MSB-first**；共 320 bit。

## §7 约束求解：什么时候用 z3

### §7.1 决策表

| 情况 | 用什么 | 为什么 |
|---|---|---|
| 纯线性（GF(2) 上只有异或） | **高斯消元** | 毫秒级，不用 z3 |
| 含 `and`/`or`/`mul`/比较/mux | **z3** | 这是 z3 的主场 |
| 未知量 < 32 bit | **直接爆破** | 比建模快 |
| 未知量 > 200 bit 且强非线性 | z3（可能很慢） | 要做好超时心理准备 |
| 未知量很多但**实际只用到低位** | **先降维**（见 §7.2） | 能把不可做变成可做 |

### §7.2 降维技巧（**最高价值**）

**① 找窄化转换**：只要出现 `(byte)` / `& 0xFF` / `ToByte` / `stelem.i1`，
就说明高位被丢弃 ⇒ 未知量按位宽缩水。

> 本战例：`ParseKey` 是 `key[i] = (keys[i] >> (j*8)) & 0xFF`，
> 只取每个 `ulong` 的**低 4 字节** ⇒ 3×64 bit 的未知量瞬间变成 **96 bit**。

**② 找取模**：`% N` / `& (N-1)` ⇒ 周期化，未知量按 N 折叠。

**③ 找早期退出**：`if (reg[i] != const[i]) break;` ⇒ 只需满足**前缀**。

**④ 约束数与未知数比较**：
- 约束 >> 未知 ⇒ 多半有**唯一解**，但要**枚举验证唯一性**（见 §8）
- 约束 < 未知 ⇒ 解很多，**必须**找出题人"真正想要的"那一组（通常靠额外的字面量/语义约束）

### §7.3 z3 建模的通用骨架

```python
from z3 import *
s = Solver()
s.set('timeout', 600000)          # 一定要设，否则可能永久挂住
UNK = BitVecs('a b c', 64)
# ... 用 Concat/Extract/LShR 表达移位与拼接；用 BitVecVal(0,8) 初始化数组 ...
for j in range(len(TARGET)):
    s.add(data[j] == TARGET[j])   # 约束：输出流 == 二进制里的常量
r = s.check()
if r == sat:
    for k in range(8):            # ★ 枚举多个模型，检查关键字段是否稳定
        m = s.model()
        ...
        s.add(Or([v != m.eval(v) for v in UNK]))   # 屏蔽当前模型继续找
```

**常见 z3 坑**：
- 移位量 ≥ 位宽是 UB，`LShR(x,64)` 会得 0 → 别用 64 表达"清零"。
- `Extract(hi,lo,x)` 参数是 **(高位, 低位, 变量)**，写反了结果完全不同。
- 1 bit 的 `~X1` 就是 `1 - X1`（`~` 在 1 bit 上是取反，OK；但与其他宽度混用会出错）。
- `BitVecVal(0,8) << 1 | bit` 必须保证两侧同为 8 bit，否则报 sort 不匹配。

## §8 验证清单（**红线：不通过不算解出**）

出结论前必须**全部**打勾：

- [ ] **独立复算**：用另一条路径（通常是纯 Python 整数）重跑算法，断言与二进制常量逐字节相等
- [ ] **唯一性**：如果用了求解器，枚举 ≥5 个模型，确认"我需要的字段"是否稳定
- [ ] **来源可追溯**：用 `re.finditer` 在**原始附件**里反查关键常量，证明它真的来自题目而非我拼出来的
- [ ] **格式自洽**：flag 是否符合赛事格式（`flag{...}`）；如果是 GBK/UTF-8 文本，是否全部可打印
- [ ] **反向验证**（可选但最强）：把解代回"加密方向"，看能否重新生成出原始密文/常量

**不合格的"验证"**（一律不算）：
- "解出来是乱码 → 换一个密钥试试"
- "结果看起来像 flag"
- "我脚本里断言了一下"（但断言的是我自己写的过程，没有交叉源）

## §9 常见错误对照表（踩过的坑，按现象查）

| 现象 | 真实原因 | 修法 |
|---|---|---|
| `TypeError: ... NoneType + int` | `r2o()` 返回 `None`（RVA 落进未映射区）或 **FieldRVA 列顺序写反** | 查节表；确认 schema 是 `[RVA, Field]` |
| 反汇编到一半 `op=0x72` 就乱了 | 小/大方法头判错，或 `ldstr` 偏移没 `& 0xffffff` | 判 `(b0 & 3) == 2`；`ldstr` 用 token 低 24 位 |
| `openssl ... bad encrypt` | `Padding=Zeros` 却没用 `-nopad`；或输入长度不是 16 的倍数 | 加 `-nopad`；检查截断 |
| `ModuleNotFoundError: Crypto / z3` | 本机没有 pycryptodome；z3 只装在托管解释器 | 用 `openssl` CLI；用托管 python 跑 z3 |
| `decode()` 抛 `UnicodeDecodeError` | `#Strings` 堆不一定全是 UTF-8 | 用 `'utf-8','replace'` 或 `latin1` |
| Python 写的 `/tmp` 和 Git Bash 的 `/tmp` 不是一处 | Windows Python ≠ MSYS 路径 | 一律用绝对路径 |
| Bash 里 `ls`/`grep`/`date` 都 `command not found` | 本机 PATH 被污染 | 命令前加 `export PATH="/usr/bin:/bin:/c/Windows/System32:$PATH";` |
| 爆破脚本跑完"全失败"却花了 1 分钟 | **分诊没做就爆破** | 先走 §2.1 与 §4.3 的 `set_Mode/set_Padding` |

## §10 crackme 补充条目（2026-10-11）

### §10.1 32↔64 位段切换 crackme（题：HTV2020-x96）

- **判据**：ELF32 但**无 section header**（`e_shoff=0`），且入口附近出现 `cmp cs, 0x23` 紧跟 `retf`
  （或反过来的 `cmp cs,0x33 / retf`）→ 这是把执行流在 **32 位段 ↔ 64 位段**之间切换。
  `0x23`=32 位代码段、`0x33`=64 位代码段（GDT 选择子）。
- **动作**：
  1. 从 ELF 头取 `e_entry`，手工反汇编入口的短短几字节确认段切换；
  2. 记下 `retf` 的目标 `段:偏移`（如 `0x33:0x804806c`），到达后**按 64 位指令流**反汇编；
  3. 校验循环里若有 `ror64(常量, i) & 0xff` 之类，逐字节反推输入；
  4. 在 **32 位 ELF compat 环境**（如 Kali）实跑，见到正确提示才算过。
- **失败分支**：把无 section header 当"损坏文件"直接放弃；或对 64 位段用 32 位反汇编器解码（指令长度全错）。

### §10.2 自校验 crackme：让程序"编码输入再比对常量"（题：QWB-crackme-task_qwxf）

- **判据**：`main` 里 `scanf("%s")` 读输入 → 调一个函数（编码/哈希/变换）→ 结果与**写死的常量串**
  逐字节比对（如 `for i in 0..0x2c`）。
- **动作**：不要在比对处硬爆；直接**对常量串做逆变换**得到正确输入。
  本题是 base64：正确输入 = 目标 base64 串的 `b64decode`。
- **陷阱（必查）**：栈上可能写死**诱饵串**（如 `qiangwangxianfengjiushini`）全程**未被引用**。
  判断某字符串是否真参与逻辑，要看它**被哪条指令引用**，别一看到"像答案的串"就当结论。
- **验证**：本地实跑，输入正确输入应输出程序的成功提示（本题 `yes, you are!`）。
