# CTF 系统登录后自动恢复

## 已验证

Windows 登录后自动启动已经安装，无需先打开 Codex 或 WorkBuddy。安装时的一次管理员授权已完成，日常启动由已登记的计划任务执行。

| 顺序 | 行为 |
|---|---|
| Windows 启动 | VMAuthdService、VMnetDHCP、VMware NAT Service 自动启动 |
| Windows 登录 | CTF-OS-常驻 启动统一接口，普通用户权限；失败后有三次重试 |
| 登录后 5 秒 | CTF-Stack-Autostart 复用或启动 Muteki、Kali 两台 VM，使用无图形启动模式 |
| 客机可达后 | 启动已有 Web/Docker 服务及 coding2api 容器；仅在缺少原 bridge 连接时修复连接 |
| 就绪检查 | 确认 CTF-OS 工具清单、Kali 核心命令/模块、Muteki Web、Coding2API 健康接口与启用席位绑定 |

原来的问题有实际证据：旧 CTF-OS 任务没有登录触发器；Startup 中 VBS 的中文路径已乱码；三个 VMware 基础服务是 Manual。旧的重复 Startup 入口已备份并移出启动目录。

使用：

- 平时：开机并登录 Windows，服务在后台启动。
- 手动恢复：双击桌面 **CTF系统-启动**，或根目录 **启动CTF系统.bat**。
- 打开工作台：http://192.168.26.130:3001。
- 看启动结果：`[CTF_ROOT]\logs\startup\latest.json`。核对本次时间，`status=ready` 表示启动检查通过；`failed` 的 `components/error` 说明失败位置。
- agent 接手后仍调用 CTF-OS `status` 取得当前在线证据。启动结果不等于模型已成功解题。

重复启动保护已验收：现有 CTF-OS PID 16608 未变，两台 VM 的 reused 均为 true；没有重启容器或清理运行中的 Worker。端口被其他程序占用时记录失败，不强杀该程序。

本次计划任务实际执行的启动检查耗时 **4.76 秒**，状态 ready；当时虚拟机已经运行。这是温启动检查，不是整机关机后的启动时间。13 项生命周期回归测试通过，覆盖重复启动、端口冲突、超时失败、Kali 依赖缺失、跨进程锁和 SSH 公钥校验。PowerShell 安装/入口脚本语法检查通过。

入口和配置：

- `tools/ctf_bootstrap.py`：有界等待、启动编排、接口常驻监督、实际健康检查与 JSON 日志。
- `tools/Start-CTFStack.ps1`：手动或计划任务入口。
- `tools/Install-CTFAutostart.ps1`：注册/回滚任务和服务启动模式，需要 Windows 管理员权限。
- `config/startup.json`：账号 SID、路径、任务名、等待时间；Kali 继续读取既有配置。
- `logs/startup/installation.json`：安装结果；`install-backup/` 保存原任务 XML、服务启动类型和原启动器。

这轮没有修改模型配置；当前 Step 席位 binding ok。没有模型推理、派题、调试目标或 flag 提交。
