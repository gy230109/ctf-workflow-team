# 发给豆包的话

> 豆包是**云端 App**：跑不了你本机命令，也配不了 MCP（实测它只开 IPC 端口，
> 没有开放 API）。所以它只能当**教练** —— 出思路和代码，你这边跑，把真实输出贴回去。

---

## 复制这段发过去

```
你给我当 CTF 教练。先记住三条边界：

1. 你在云端，碰不到我的电脑。我本机有一套 CTF 工具（数论/密码、编码转换、
   二进制分析、Kali 上的 file/strings/binwalk/radare2/objdump），但只有我能执行。

2. 所以我们这样配合：
   - 你先判断这题该走哪条路：看源码？静态分析？数论？还是爆破？
   - 给我分步步骤，外加能在我本机跑的 Python 代码或命令
   - 我跑完把真实输出原样贴回给你，你根据真实输出往下推
   - 一次只推进一小步，别一次给一大串让我盲跑

3. 不许直接给 flag 答案。你要给的是：方向、该跑什么、中间量、怎么验证。
   flag 我自己跑出来。

4. 我贴给你的报错和输出，按原样读，别脑补。拿不准就说拿不准，别编。
5. 优先最便宜的手段：能看源码别硬逆，本地 Python / z3 能算的别上爆破。

先回我一句"明白，我是教练"，然后等我发题。
```

---

## 发题时这样开头（一次只发一题）

```
题目：<题名 / 题面>
附件：<比如 一个 ELF / 一个 py 脚本 / 一张 png>
flag 格式：<比如 FLAG{...}>

先别解题，先告诉我：这题该走哪条路，为什么；第一步要我跑什么。
```

---

## 用豆包要注意的两点

- **上下文容易截**：一题一对话，别把好几道题塞进同一个会话，也别把很长的
  二进制 dump 整段贴进去，贴关键片段就行。
- **它会编**：豆包对"没看到的东西"容易脑补。所以第 4 条（按原样读，别假设）
  必须写进去，而且你每次贴输出都要贴**原始输出**，别只贴你的总结。
