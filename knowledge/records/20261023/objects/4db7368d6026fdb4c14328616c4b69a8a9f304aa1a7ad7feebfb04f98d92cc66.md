## 遇到的故障与处理

1. DeepSeek 最初返回上游 400，具体要求是首条消息必须为 system。新网关的独立启动适配仅在缺少 system/developer 时补中性默认 system，保留已有消息；普通 Chat Completions 与 Responses 随后均返回 200 / OK。
2. 原生 Codex+DeepSeek 仍被上游明确以 `11128 / Illegal API invocation from an unapproved channel` 拒绝。保留失败配置 disabled；同一模型改由 Claude Code 后通过真实回复和工具往返。未把普通 Responses API 的成功当成 Codex CLI 成功。
3. Step 的 Kilo 通路出现模型冷却，Zen 也出现 429 / Endpoint is unavailable。Step Key 仅放行本模型，由目录选择 Kilo/Zen 可用渠道。真实 CLI 与一次 Bash/Python 往返均通过；仍作为备用席，不默认并发。 限流失败保留在 `tests\step-tool-roundtrip-kilo-failed.json`，不能据一次通过认定该免费上游长期稳定。

## 调度与职责

采用 WorkBuddy 源码核查的主解题+串行复核方案：只有 GLM 带普通角色且启用；DeepSeek 只带 review，复核时占同一并发额度；Step disabled，按需在独立轮次选择。派生 `max_workers=1`，`start_workers=1`、`max_total_workers=0`、`dispatch_mode=fixed`。CTF 的 auto 会强制并发 3，因此本方案用 fixed。review.engine 填实际席位 name。

每次切换保存 before/after 并回读 API；失败席位禁用，回滚使用原 Pi 快照。WorkBuddy 负责配置应用、preflight 与下一批 CTF 的题目/预算登记；Codex 负责新网关及协议修复。配置已应用，独立回读时间为 2026-10-11T16:07:35.935112+08:00；证据见 `D:\Apps\Coding2API-Local\tests\dispatch-activation-readback.json`，WorkBuddy 的执行回填在 `协同\workbuddy-status.md`。
