## 1. 结论

> **程序预期输入：** `{i_l0ve_you}`
> **平台 Flag：** `flag{i_l0ve_you}`

程序流程：`输入 → base64 编码 → 逐字节加上下标 → 与常量比较`。

```c
printf("please enter the flag:");
scanf("%s", input);
b64 = base64Encode(input);            // 标准字母表 + '='
for (i = 0; i < strlen(b64); i++) b64[i] += i;      // 0x4157fb
if (strcmp(b64, "e3nifIH9b_C@n@dH") == 0) printf("rigth flag!");

```

## 5. 已验证事实

1. **变换链**：`输入 --base64--> e2lfbDB2ZV95b3V9 --每字节 += i--> e3nifIH9b_C@n@dH`（与 .data 中常量逐字节一致）。
2. **外部独立复算**：对 `{i_l0ve_you}` 正向执行 base64 + 加下标，结果等于二进制内密文（True）。
3. **实机双向验证**：`{i_l0ve_you}` → `rigth flag!`；任何多余/缺省字符 → `wrong flag!`。
4. 密文长度 16 → base64 去 padding 后长度 16 ⇒ 明文 **12 字节** = `{i_l0ve_you}`（数学自洽）。
5. 该程序 **32 位、无壳、无反调试**，是纯算法题。

## 6. 这道题的坑

1. **flag 前缀不在程序里**：程序比较的串是由 `{i_l0ve_you}`（12 字节）编码而来，**不带 `flag`**。
   所以：
   - 喂给程序的输入 = `{i_l0ve_you}`
   - 提交给平台的标准 flag = `flag{i_l0ve_you}`
   实机已证实输入 `flag{i_l0ve_you}` 会被判 `wrong flag!` —— **别把二者搞混**。
2. **PE 的文件偏移 ≠ RVA**：我第一次直接拿字符串的文件偏移当 RVA 去 grep 引用，**0 命中**。
   必须先过区段表换算（`RVA = sec.VA + (off - sec.Raw)`，`VA = ImageBase + RVA`）。
3. **`scanf("%s")` 会在空白处截断**：输入不能含空格/换行，且**必须恰好** 12 字符（多了少了都错）。
4. 提示语 `rigth flag!` 是**出题人拼写错误**（right → rigth），按原文搜索字符串时别"顺手纠正"，否则搜不到。

## 8. 复现要点（方法）

```python
import base64
c = "e3nifIH9b_C@n@dH"                                   # .data 常量
b64 = bytes((ord(ch) - i) & 0xff for i, ch in enumerate(c))
flag_in = base64.b64decode(b64)                          # b'{i_l0ve_you}'
# 正向闭环验证
assert bytes(((base64.b64encode(flag_in)[i] + i) & 0xff) for i in range(16)).decode() == c
print("程序输入:", flag_in.decode(), " 平台 flag: flag" + flag_in.decode())
```

定位手法（32 位 PE，无符号表时）：
```bash
objdump -d -M intel reverse_3.exe > full.asm
# 先算字符串 VA（过区段表），再 grep "push <VA>"
grep -n "417b74" full.asm     # → 415758: push 0x417b74  即 main 内第一个 printf
```

## 9. 复盘：可复用的判断

| 触发信号 | 含义 | 动作 |
|---|---|---|
| 代码里出现 64 字符 `ABC…xyz0123456789+/=` 常量 | 程序内做了 base64 | 找它被谁引用 → 即 base64 函数 |
| 密文长度是 4 的倍数、字符集属 base64 | 密文是 base64（可能还叠了别的变换） | 先试 **抵消外层变换**（本例 `-= i`）再 b64 解码 |

## 11. 收尾三问

1. **触发信号**：程序里同时出现「base64 字母表常量」+「一段不可打印/非常规密文」→ 先怀疑 **base64 + 外层字节变形** 的组合，别一上来就硬逆。
2. **可迁移性**：
   - 无符号表的 32 位 PE，**用字符串找引用**是最快的 main 定位法（`push <字符串VA>`），前提是先把文件偏移换算成 VA；
   - "外层变换（加/减/异或下标或常量）套 base64"是 CTF 逆向的常见组合，**逆序逐个抵消**即可，不需要爆破。
3. **边界 / 失败分支**：若外层变换依赖读取时的状态（如上一字节），需按顺序整体反演；若 base64 是**换表**的（对比表首字符），先映射回标准表（见战例 `CTF-Reverse-特殊的Base64`）；若密文长度不是 4 的倍数，先确认 padding 规则再解。
