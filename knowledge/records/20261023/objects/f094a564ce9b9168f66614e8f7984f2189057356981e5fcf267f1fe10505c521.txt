===== 已确认的客观事实（可直接采用，不必重复验证）=====

1. game.gb 是结构合法的 Game Boy ROM：任天堂 Logo 完整；头部校验 0x014D=0xCC 复算一致；
   全局校验 0x014E=0x830E 复算一致（说明文件未被事后改动）。
   title@0x0134="GAME"；cart_type@0x0147=0x00 (ROM ONLY)；rom_size@0x0148=0x00；
   entry@0x0100 = `00 C3 50 01` (JP 0150h)。

2. ROM bank1（0x4000-0x7FFF）整块 0xFF，完全未使用。**全部内容都在 0x0000-0x3FFF 这 16 KB 内。**

3. 这是 Flappy Bird 类小游戏，名字 **FlappyPig**。用 pyboy 跑通：
   - 标题画面显示 "FlappyPig"（图形 logo）与 **"PRESS START"**（等宽字体文字）；
   - 按 START 进游戏：横版城市背景 + 小猪；
   - 死亡后显示 "RESULT" / "BEST" 分数。
   - 屏幕读取：`pb.screen.ndarray`（属性）；图块图在 **0x9800**（32×32）；
     VRAM tile 数据 0x8000-0x97FF。

4. 🔴 **前一版 prompt 里说的"BG 图块索引 33..70 正好对应 ASCII 33..70"是错的，作废。**
   实测这个游戏的**字体表不是 ASCII 顺序**。正确读法见下面第 8 条。

5. 两个 mp3 的 ID3v2.4 标签在偏移 138 处结束（syncsafe size=128）。
   源元数据 major_brand=mp42 / Lavf56.25.101 / LAME3.99.5，由 MP4 抽轨而来。

6. kun.mp3 与 man.mp3 **不是同一段音频的微改**：从偏移 184 起就不同；
   同长度区间仅约 1.6% 字节相同（接近随机基线）。
   **长度差 = 84428 字节 ≈ 5.3 秒**（man 比 kun 长）。

7. kun.mp3 整段波形包络几乎恒定；man.mp3 前 6 秒静音后渐入。
   🔴 **两首的频谱图已经做过了，结论是「没有频谱隐写」**（`ffmpeg -lavfi showspectrumpic`
   出图人工看过，都是正常音乐的宽带能量，无文字/图案/摩斯）。**不要重复做频谱图。**

===== 🔴 关键突破：字体表 + ROM 里唯一一段"非游戏文本" =====

**（这一节是本轮的核心线索，请以此为起点。）**

### 8.1 GB 字符读取的正确姿势（前一轮就是在这里栽的）

- `LCDC`（0xFF40）的 **bit4 = 0** → tile 数据基址是 **0x8800（有符号模式）**。
  正确算法：
  ```
  n <  128 : VRAM 地址 = 0x9000 + n*16
  n >= 128 : VRAM 地址 = 0x8800 + (n-128)*16
  ```
  **不是 `0x8000 + n*16`。用错地址会读到全 0 的空白 tile，从而误判"字体没加载"。**

### 8.2 实测出来的字体映射（标题画面与游戏画面**完全一致**，稳定可复用）

| tile | 字符 | | tile | 字符 |
|---|---|---|---|---|
| 65 | P | | 76-85 | '0'-'9' |
| 66 | R | | 86 | U |
| 67 | E | | 87 | L |
| 68 | S | | 88 | B |
| 69 | T | | 71-75 | 点 / 冒号 / 分号 / 网底 / 实心块 |
| 70 | A | | 138,139 | 两个竖线条图案 |

这个字符集**恰好够拼** "PRESS START"、"RESULT"、"BEST" —— 作者只做了这 9 个字母的字库。
验证方式：标题画面 tilemap 的 row31 = `65,66,67,68,68,0,0,68,69,70,66,69`
→ 按上表读 = `P R E S S _ _ S T A R T` ✅ 与屏幕实拍一致。

### 8.3 用正确映射重读 ROM 里的 `36 xx` 内联序列（以下都是**事实**，不是猜测）

| ROM 偏移 | tile 序列 | 按 ASCII 读（错） | **按游戏字体读（对）** | 含义 |
|---|---|---|---|---|
| 0x1A4B | 66,67,68,68,68,69,70,66,69 | `BCDDDEFBE` | **`RESSSTART`** | 游戏 UI（"PRESS START" 后半） |
| 0x1DA2 | 67,68,86,87,69,88,67,68,69 | `CDVWEXCDE` | **`ESULTBEST`** | 游戏 UI（"RESULT"/"BEST"） |
| **0x1C92** | 65,68,76,79,66,80,85,86,67,81,83,82,66,80,78,77,66,67,84 | `ADLOBPUVCQSRBPNMBCT` | **`PS03R49UE576R421RE8`** | **⚠️ 不是任何游戏 UI 文本** |

- 0x1C92 那段前后各有一个 tile：`0x8A`（138）和 `0x8B`（139），实测是两个**竖线条图案**。
- 该段代码结构：`LD A,$8A; LD (DE),A` 写头，逐个 `LD (HL),$xx` 写 19 个 tile，
  最后 `LD (HL),$8B`，然后 `PUSH BC / LD HL,$0706 / LD HL,$0507 / CALL $33A7`
  —— `$33A7` 是往 VRAM 背景图块图写数据的例程（`0x3385` 那段等 STAT 是它的前导）。
  → 语义 = **在背景层 (x=7, y=5) 画这串字符**。

### 8.4 由此得出的结论

**`PS03R49UE576R421RE8` 是整块 ROM 里唯一一段"不是游戏界面文本"的字符串。**
它不是待解密的密文，就是游戏自己会画出来的字符序列。19 个字符。

请以此为起点继续：
- 这串 19 字符是什么？它是不是 flag 的载体？
- 观察到的特征（供参考，不要被限制）：数字 0-9 几乎齐全；字母只用到了 P、S、R、U、E；
  长度 19；两侧被竖线条图案夹住；写入坐标 (7,5)。
- 也要考虑：**游戏还有哪些 `set_bkg_tiles` 调用点从未在正常流程里被触发**
  （已知调用点：`$33A7` 背景图块、`$3342`/`$335F` 批量复制、`$0E4A`、`$230B`、`$23BA`、`$2388`）。
