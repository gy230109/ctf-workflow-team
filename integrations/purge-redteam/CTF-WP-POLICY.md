# CTF 解题能力与 WP 书写双模块规范（2026-10-30）

主线：读题与附件 → 分析和解题 → 取得候选 flag → 原程序或平台验证 → 交付规范 WP。
模块一是解题能力：完整融合传统 CTF 与破甲能力。按本题需要充分调用工具、POC、
工具链和角色协作，破甲可以承担主力；不设辅助位或仅内网题才能协作的限制。
依赖、执行与验证依据实际结果核对。统一目标是得到并验证本题 flag，最终交付 WP。

模块二是 WP 书写：在解题中同步保存原始证据与必要截图，按主线形成规范题解。

WP 同步编写，包含题目信息、原题与附件摘要、解题概述、分析思路、解题方法、
关键解题过程、最终结果、验证和复现说明。正文五类章节为 overview、analysis、
solution、validation、reproduction；观察与章节必须引用真实 source_step/source_steps。

在必要且合适的关键线索页面、关键操作/调试画面和结果页面保留真实截图；
不为每次状态查询、记账或后台计算机械截图，不为凑图重复执行操作。
关键操作执行时，立即保存真实窗口、浏览器、终端或 VM 中与本步有关的截图；
取得 flag 后，保存实际结果画面。浏览器与已支持调试器已有自动采集就复用原图。
其他截图通过 wp_capture 保存，带 source_step 和 stage=process 或 result；
result 必须关联本题实际执行步骤。一张图确实同时展示过程与结果时，使用
stage=process_and_result 共同引用，不强制再拍第二张。每张图保存原文件、来源、时间线步骤与 SHA256，
Word 正文嵌图并添加图注和步骤关联。调用返回的 screenshot_guidance 提示当前步骤。

截图必须展示该步实际画面，并审阅像素是否可读、是否对应输出。后台命令的回放、
日志渲染图和结构化 JSON 都保留为辅助证据，不称为真实截图。
没有可见结果窗口时主动选择合适真实窗口/终端采集，不用无关桌面照片充数。

规范导出需五类正文、行动目的、观察引用及过程截图；已有 flag/正确回执时还需
关联结果步骤的截图。截图失败保留原错误，继续保存解题结果，不重复执行有副作用
的动作来补拍。allow_incomplete=true 可交付明确标记的缺项草稿；不能声称完整。
截图与稿件完整不认证 flag。候选、本地验证、真实平台 correct 回执分别登记。
